# ADR-0036: DWG is a crate of our own, `cad-dwg`, written from the Open Design Specification; LibreDWG and acadrust are its test oracles, not its dependencies

**Status:** Accepted (2026-10-20)  
**Date:** 2026-10-20  
**Kind:** Evidence (resolves DESIGN §40, FUTURE; amends §24.3)  
**Design refs:** §3, §24, §40, §43, §44, §46

## Context

DWG is what AutoCAD and most of its users exchange. CadSlate2D reads DXF of any release and writes DXF R2000 (ADR-0018). A drafter handed a `.dwg` must convert it elsewhere; one asked for a `.dwg` cannot send one. The user asked for both directions in the AutoCAD 2000 (`AC1015`), 2004 (`AC1018`), and 2007/2008 (`AC1021`) formats (#250, 2026-10-18).

The design deferred the question: §24.3 "DWG is explicitly deferred", §40 FUTURE, and §44's warning that a DWG dependency must not decide the project model. With the licence settled (ADR-0035, AGPL-3.0-or-later), the question is only how.

DWG is undocumented by Autodesk. Three sources exist:

- **The Open Design Alliance's *Open Design Specification for .dwg files*, version 5.4.1**, freely published, 270 pages, covering R13 through R2018. It is complete enough to write a reader from, and in places wrong or silent (below).
- **LibreDWG** (GPL-3.0-or-later, C, the GNU implementation, under development since 2009; the development source of 2026-10-13). Reads everything from R1.1 to R2018; writes R13 through R2004 ("good enough for everything but R2007", its README). It builds here with CMake once its `jsmn` submodule is fetched; there is no Debian package.
- **Pure-Rust crates on crates.io**, new since this project began: **acadrust 0.6.5** (MPL-2.0; first published 2026-02; 211,000 lines; DXF and DWG, R12 through R2018, read and write; 135 stars, 70 forks, 10 contributors, 44,800 downloads; CI builds for `wasm32-unknown-unknown`), and **cadkit-dwg 0.3.5** (MIT or Apache-2.0; 2026-10-01; a clean-room reader for R14 through R2018, no writer).

The ODA's own Drawings SDK is commercial and closed, and out of the question for a free, open application.

## The spike

One day, 2026-10-20, one file of 1,358 lines of Rust with no dependencies, written from the specification with LibreDWG's source read only where the specification and the file disagreed. It reads the three containers and decodes the object map, layers, lines, circles, arcs, lightweight polylines, and text. The measurements:

| What | `AC1015` | `AC1018` | `AC1021` |
| --- | --- | --- | --- |
| LibreDWG's `example_*.dwg`: size, objects in the map | 583 KB, 750 | 188 KB, 735 | 456 KB, 540 |
| Container: locate and decode the sections | 0.27 ms | 0.69 ms (13 sections, 26 pages, LZ77) | 0.76 ms (13 sections, 22 pages, Reed–Solomon and the R21 compressor) |
| Objects: decode every object in the map | 0.54 ms | 0.54 ms | 0.52 ms |
| What it decoded, against the DXF AutoCAD wrote of the same drawing | 68 LINE, 5 ARC, 1 CIRCLE, 11 LWPOLYLINE of 3,712 vertices, 2 TEXT, 5 LAYER: every count and every coordinate equal | the same | the same (one of five layers refused: its string stream) |
| LibreDWG's sample files of the format read without a panic | 22 of 22 | 21 of 21 | 18 of 18 |
| 10,000 entities (the samples' lines, arcs, circles, and polylines, repeated) | 41 ms | | |
| 100,000 entities | 435 ms; peak RSS 73 MB, of which the synthetic section is 70 MB | | 494 ms |
| The decoder as WASM (`opt-level = "z"`, LTO, `panic = "abort"`) | 64 KB, 24 KB gzipped | | |

The 10,000 and 100,000 figures are decoding only, into values; building the drawing is the DXF reader's cost on top, and the exit re-measures on the benchmark drawings once the writer exists.

**Where the specification is wrong or unclear**, found by the spike and confirmed in LibreDWG:

1. §20.4.1 says the entity's "nolinks" bit "always has value 1" in R2004+. It is not stored at all.
2. §2.11 says an entity colour's RGB value is a bitshort. It is a bitlong.
3. §23.1 leaves open whether an object map section's size counts its own two bytes. It does.
4. §5.10.1's table of byte orders inside a literal run is real: the R21 decompressor permutes every run it copies, and a straight copy produces nonsense.

The crate keeps this list in `docs/dwg-matrix.md` and grows it.

**acadrust, measured the same way.** It reads the three example drawings completely, 211 entities of 28 kinds each, in 15 to 34 ms with 13 to 16 MB peak RSS; reads 56 of the 61 sample files, and the other five fail whole (a parse error in one object fails the file); writes each drawing back in its own version with identical counts, and refuses to change version when the file holds a custom object it keeps raw; its output is read by LibreDWG's `dwgread` without an error and by the spike with identical counts. 100,000 lines: written in 56 to 87 ms, read in 61 to 232 ms, 204 to 213 MB peak RSS. As WASM, DWG reading and writing with default features off: 3.54 MB, 1.22 MB gzipped. The application today is 2.16 MB, 0.81 MB gzipped.

## Decision

1. **A crate of our own: `cad-dwg`**, beside `cad-dxf`, a host-side pure Rust crate like every crate but `cad-wasm` (ADR-0001, ADR-0002), written from the Open Design Specification. It reads and writes `AC1015`, `AC1018`, and `AC1021`. Later versions are refused with a structured error that names the version; nothing in this decision stops a later ADR adding them, since R2010 and after are the R2004 container with R2007's object coding.
2. **DWG is a second encoding of the same records, not a second model.** The specification gives every field its DXF group code, so the DWG reader feeds the record the DXF reader finishes (`RecordBody` and `finish_record` in `cad-dxf`), and what a layer, a dimension, or a layout *means* is written once: `cad-dwg → cad-dxf → cad-document`. The same `Drawing`, the same `ImportReport`, the same limits (DESIGN §43, as `ImportLimits`), the same rule that what the drawing cannot hold is reported and never guessed at. The writer walks the `Drawing` as the DXF writer does and encodes by the object prescriptions; what it shares with `export.rs` is settled in its issue.
3. **LibreDWG and acadrust are oracles, not dependencies.** Neither ships:
   - **acadrust** is a dev-dependency of `cad-dwg`: it writes the fixtures under `test-data/dwg/` from the DXF fixtures, in all three versions, through an example binary run deliberately like the screenshot baselines; and the tests read our output back through it, so "read by an independent reader with nothing lost" is a test, not a ritual. MPL-2.0 is compatible with the AGPL and joins `deny.toml`'s allow list for that reason; `about.toml` already leaves dev-dependencies out of the notices.
   - **LibreDWG**'s `dwgread` and `dwg2dxf`, built from source, are the second reader, run by a script over the fixtures and our output; a disagreement between the two oracles is investigated, never averaged.
   - **AutoCAD or DWG TrueView** stays the one check that needs a person, as #232 does for DXF.
4. **The file commands** follow DESIGN §24: `OPEN` recognises a DWG by its first six bytes whatever its extension; `SAVEAS` offers DXF R2000, DWG 2000, DWG 2004, and DWG 2007 (the file picker's types where the browser has one, a prompt option where it downloads); `SAVE` writes the format the file came in. Output is deterministic for the same drawing, and export → import → export is byte-identical for the fixtures, as for DXF.
5. **Budget.** The crate adds under 500 KB of WASM, gzipped under 200 KB, measured in the exit against the spike's 24 KB; and reads the 100,000-entity benchmark drawing in under a second of decoding on the host.

## Alternatives considered

- **acadrust as the implementation.** The fastest path: an adapter between its `CadDocument` and our `Drawing`, with every entity kind already read and every version written. Rejected on the measurements: it would add 1.22 MB gzipped to a 0.81 MB download, hold 2 KB per line entity while a file loads (WASM memory never shrinks), fail whole files on one bad object where §24.2 wants a report, and tie the project's file format to a 0.x API with 54 crates beneath it. It is exactly right as an oracle.
- **LibreDWG, compiled to WASM.** Licence-compatible since ADR-0035, but a C toolchain in the build, a C parser in the fuzz surface, megabytes of WASM for formats back to 1986, and no R2007 writer. Rejected.
- **cadkit-dwg.** A reader only, three weeks old. Watched, not used.
- **The ODA Drawings SDK.** Closed and commercial. Rejected.
- **Read DWG, write only DXF.** Half of what was asked. Rejected.
- **Our own reader and acadrust's writer.** Two models and two licences for one feature, and the writer is the half that must satisfy AutoCAD, so it is the half worth owning. Rejected, but see below.

## Consequences

- A new crate and a new layer line, `cad-dwg → cad-dxf`, in AGENTS.md and `scripts/check-boundaries.sh`; `cad-wasm` takes `cad-dwg`.
- `docs/dwg-matrix.md`: one row per record kind and per version naming its test or fixture, as `dxf-matrix.md` does, and the specification errata.
- A fuzz target for the reader on bytes, like the DXF one (DESIGN §41): arbitrary bytes never panic; every count a file can grow is bounded.
- `cad-dxf`'s `RecordBody` and `finish_record` become an interface between crates, which is the one place DWG changes DXF code.
- `deny.toml` allows MPL-2.0; `README.md`'s prerequisites mention LibreDWG only for the optional script.
- The `AC1021` writer is the hardest piece in the plan: Reed–Solomon encoding, 64-bit CRCs, the random encoder, and the string streams. It comes last. If it cannot be validated against both oracles, the application ships reading all three and writing `AC1015` and `AC1018`, and a new ADR weighs acadrust's writer for `AC1021` alone against its size.

## Revisit when

- A user needs `AC1024` or later written; reading them is the same decision and a small addition.
- Encrypted or password-protected drawings are asked for (§4.1's security flags; not read today).
- acadrust reaches 1.0 with a stable model and a WASM build under a few hundred kilobytes, which would reopen the first alternative.
- The `AC1021` writer cannot be validated (above).
